# 03 - Production and streaming

**Status (2 September 2026):** built and live. Two tools, both verified on
production; the rest of this document says what each is, where it lives, and
what the earlier plan asked for that is not built.

The earlier version of this file opened with "Nothing built" and planned routes
like `/tournaments/production?id=` that the slug rule forbids. It is replaced
rather than amended, because a plan for something that now exists is worse than
no plan: it tells the next person to build it again.

---

## What production is

An organiser streams a tournament or an event through OBS, vMix or anything that
takes a browser source. V-ENT gives them two ways to put graphics on that stream:

| | Studio | Overlays |
|---|---|---|
| What | Eight graphics V-ENT draws itself, driven from a console | An HTML file the organiser owns, filled by V-ENT with live data |
| For | An organiser who wants a scoreboard in ten minutes | An organiser with a designer, or who wants it to look like theirs |
| Where | Tournament console, Production tab | Tournament console, Production tab; event console, Overlays tab |
| Auth on air | Session token in the URL | Overlay token in the URL |

A browser source has no cookie, no session and no header, so whatever authorises
an on-air page is in its URL. Both tokens are long, random, and can be retired.

Entry point for a person: `/production`, which explains both and lists what the
signed-in person runs with a way into each console. It is `noindex` and in the
robots disallow list, because it is a personal list.

## Studio

Backend `vent_tournament/views_studio.py`, models `BroadcastSession` and
`BroadcastElement` (migration 0031). Frontend `src/components/studio/StudioPanel.js`
(the console) and `src/app/studio/[token]/[kind]/page.js` (the element page).

Four decisions, each load-bearing:

1. **State lives on the server.** The element page asks the feed what to show,
   every 1200 ms, and redraws only when `version` moves. OBS can be restarted
   mid-show and every graphic comes back exactly as it was.
2. **One request feeds every element.** Six pages polling separately on a venue
   hotspot is six chances the failed one is the one on air.
3. **The studio does no arithmetic.** Standings and live matches come from
   `views_overlay_feed.overlay_feed`, where the tournament already computes them.
4. **Starting a broadcast ends the previous one.** Two live sessions is two sets
   of URLs and no way to know which screen is which.

Element kinds: scorebar, standings, lower_third, player_card, bracket, ticker,
intro, outro. Adding a kind is an entry in `BroadcastElement.KINDS`, a component
in the element page, and a fields entry in the console.

Routes:

| Method | Path | Who |
|---|---|---|
| GET, POST | `/tournament/<ref>/studio/sessions/` | organiser |
| GET, POST `{end: true}` | `/tournament/<ref>/studio/sessions/<id>/` | organiser |
| POST `{active, payload}` | `/tournament/<ref>/studio/sessions/<id>/element/<kind>/` | organiser |
| GET | `/studio/<token>/feed/` | the element page |

Element page URLs come from `FRONTEND_URL`; the feed from the API host. They
cannot share a base, and once did: every copied URL was a 404 (BE #121).

`may_use_studio()` is where a plan check belongs when billing exists. Today it
is ownership or the `manage_tournaments` override.

## Overlays

Backend `vent_tournament/views_overlays.py`, `views_overlay_feed.py`,
`overlay_binding.py`, `overlay_templates.py`, `static/overlay-runtime.js`,
`docs/OVERLAY-PROMPT.md`. Model `TournamentOverlay` (0030; event FK in 0033).
Frontend `src/components/overlays/OverlaysPanel.js`, one component for both kinds.

An uploaded file marks its data with one attribute: `data-vent="team.name"`,
`data-vent-src="team.logo"`, `data-vent-repeat="standings"`, `data-vent-show`.
A file with no marks uploads and is reported as undriveable at upload rather than
discovered on air. A file defining `window.build()` is driven as a script.

**The vocabulary is one list, on the server.** The prompt, the runtime and the
feed are three views of it; `tests_overlay_vocabulary.py` asserts every promised
name resolves against a real feed, and `tests_overlay_templates.py` asserts every
shipped template uses only those names. The first prompt invented names the feed
never sent, and every one resolved to an empty string on air.

Templates: 8 for tournaments, 6 for events, generated by `overlay_templates.py`
so the marking cannot drift from the vocabulary. Composited over video: no
background, no stroke, no loop.

Routes, for `tournament` and for `event`:

| Method | Path |
|---|---|
| GET | `/<kind>/<ref>/overlay-feed/` (public) |
| GET, POST | `/<kind>/<ref>/overlays/` (list with prompt, field help and templates; upload, or `{template: key}`) |
| DELETE | `/<kind>/<ref>/overlays/<id>/` |
| POST | `/<kind>/<ref>/overlays/<id>/rotate/` |
| GET | `/overlay/<token>/` (the file with the runtime injected) |

## Stream links

`youtube_link`, `twitch_link`, `kick_link` on a tournament; `StreamPanel` on the
public tournament page embeds the first one set, or links out where embedding is
refused.

## Tests and checkers

`tests_studio`, `tests_studio_urls`, `tests_overlays`, `tests_event_overlays`,
`tests_overlay_vocabulary`, `tests_overlay_templates`: 98 tests. The overlay
probe `scripts/overlay-probe.mjs` opens a real upload in Chrome at 1920x1080 and
compares the rendered DOM to the feed.
